# Immich 对比分析与功能借鉴决策底稿

> 目的：以开源照片管理软件 **Immich** 为参照，盘点本项目（照片管理 0.5.8，本地离线、摄影师向）的功能差距，
> 区分「值得借鉴（理念）」与「可以借鉴并实现（可行）」，供产品决策参考。
> 撰写日期：2026-09-15。状态：决策底稿（未实施，代码未改动）。

---

## 0. 一句话结论

Immich 本质是「你自己运行的私有云相册」（仍依赖常开服务端 + 网络 + 多用户），
本项目本质是「永不联网的本地桌面整理工具」。两者**定位不同**，功能差距主要来自架构而非能力。

真正值得抄的，是 **Immich 验证过、且能在离线单用户桌面形态下直接落地的功能**；
属于「服务端/多用户/网络」的能力（共享、移动备份、公开链接）不应照搬——那等于重做产品。

---

## 1. Immich 当前状态（2026-09 核实）

- 版本：v3.0.x（2026-07 发布），GitHub ~100k stars，AGPL-3.0。
- 架构：Docker 自托管（PostgreSQL + Redis + Machine-Learning 容器）+ Web(Svelte) + Flutter 移动端(iOS/Android)。
- AI 全部本地跑：人脸识别/聚类、CLIP 语义搜索、物体识别、反向地理编码——不调用外部云服务。
- 定位：家庭/个人「Google Photos 替代品」，隐私优先（数据不出本机服务器）。
- v3 新增：非破坏性修图、自动化 Workflows(预览)、HLS 视频流、库完整性检查、「最近添加」页。

## 2. 核心架构差异（决定「能抄什么」）

| 维度 | Immich | 本项目（0.5.8） |
|---|---|---|
| 形态 | 自托管私有云（需常开服务器） | 纯本地桌面单文件 exe，零基础设施 |
| 用户模型 | 多用户 + 角色/管理 | 单机单用户 |
| 网络 | 需服务端，可外网访问 | **完全离线，无网络** |
| AI 运行位置 | 本地 ML 容器（同机） | 本地进程内（RapidOCR / YuNet / SFace / CLIP 已验证） |
| 存储 | PG + 对象存储/磁盘，存储模板可自定义 | SQLite + 原文件不动（仅扫描索引） |
| 平台 | Web / iOS / Android | Windows x86_64 / 银河麒麟 V10 aarch64 |
| 定位 | 家庭/个人相册 | **摄影师向**本地整理工具 |

## 4. 借鉴优先级（价值 × 可落地性）

### 🔴 高优先 · 贴合离线摄影师 · 技术已具备条件
1. **CLIP 接入产品 UI（语义搜索 + 零样本场景标签）**
   - 现状：CLIP 在本项目**已跑通**（`photo_embeddings` 表 + `pm clip-index/clip-search`），但 `autotag.py` 仍是路径/文件名关键词匹配——正是「标签太少不合理」根因。
   - 落地：① 高级搜索 `text:` 走 CLIP 向量 top-k；② 导入时自动生成场景标签（海边/雪山/会议/演讲…）。
   - 约束：不增服务器、不联网；体积可控（分层打包只装图像编码器 ~333MB，自由中文搜索才需文本编码器）。
2. **反向地理编码（按地名搜，而非只有坐标）**
   - 现状：地图只画点、`gps:` 搜经纬度。
   - 落地：内置离线中国省市/城市库（体积小），支持搜「北京」「西湖」「上海」。完全离线可行，对国内摄影旅行整理极实用。
3. **照片堆叠 Stacks（连拍 / RAW+JPG 合并浏览）**
   - 现状：有 dHash 去重与分组基础，但无「合并为栈、默认显示代表帧」。
   - 落地：摄影师必拍连拍与双格式输出，扩展成本低、体验提升大。
4. **回忆「X 年前的今天」**
   - 现状：基于已有时间线，按「月-日」回看往年同日。纯前端、零风险、愉悦感强。

### 🟡 中优先 · 需评估工作量/边界
5. **层级标签**：扁平 `tag:` → 父子层级，整理更系统。
6. **XMP sidecar 双向同步**：与 Lightroom/Capture One 互通元数据（评分/标签/人物）。摄影师强痛点，但需引入 exiv2/pyexiv2，且须守「只读不破坏原图」红线。
7. **库完整性校验**：扫描后比对 DB 与磁盘（缺失/改动标红），离线工具实用。
8. **归档（隐藏出主线时间轴）**：用现有 `flag:` 体系扩展 `archive` 语义，比 Immich「回收站自动清空」更契合本项目「程序内不删除」硬约束。

### ⚪ 暂不推荐 / 与定位冲突（决策时排除）
9. 多用户 / 共享相册 / 伙伴共享 / 公开链接 / 移动自动备份：需常开服务端 + 网络 + 账号体系 = 重做产品，不符离线单用户桌面定位。
10. 回收站自动清空：直接触碰「程序内无任何删除功能」红线，不建议。
11. 视频硬转码 / 非破坏性修图 / 工作流自动化：有价值但 scope 大、偏离「照片整理」核心，作远期。

---

## 5. 建议落地顺序（opinionated）

若只挑 3 件做，优先级：**① CLIP 接入 UI → ② 反向地理编码 → ③ 照片堆叠**。

- ① 技术已验证、直接解决已知痛点、零架构改动；
- ② 与 ③ 均为摄影师高频刚需、纯本地可实现、不碰红线；
- 三者都不需服务器/网络/多用户，与项目灵魂一致。

Immich 真正「厉害但抄不动」的部分（私有云、多端同步、sharing）本质是**部署形态差异**而非功能差距，不必为追而追。

## 6. 待用户决策的问题

- [x] **① CLIP 接入 UI —— 已批准启动**，模型打包策略：**图像+文本 727MB（完整模型）**。
      - 含义：同时装入图像编码器（333MB）+ 文本编码器（393MB），因此**既支持导入时零样本场景标签、也支持自由中文语义搜索**（`text:` 走 CLIP 向量 top-k）。
      - 取舍：相对「仅图像编码器 333MB」方案多 ~394MB，但换来完整中文自然语言搜索体验（如「一张海边日落的照片」），对摄影师找图更实用。
      - 体积提示：727MB 模型走分层打包，仅在用户开启 CLIP 功能时加载（ClIPService 延迟加载已验证），不增加常驻内存。
- [x] **② 反向地理编码 —— 纳入**，数据源拍板：**全球库（GeoNames 城市级 + 国家/州级，~10–30MB）**，覆盖海外旅拍；中国再叠加省/市/区+景点细化（国内精度到区/景区级）。
      - 落地：经纬度 → KD-tree 最近邻 admin/城市中心点 → 返回「国家/州/省/市/区/景点」层级地名；`gps:` 支持 `gps:北京`/`gps:西湖`/`gps:Tokyo` → bbox 查询；地图点位显地名。
- [x] **③ 照片堆叠 Stacks —— 纳入**，**只合并不删**：检测=连拍（同目录+间隔<5s+内容相似）或同 basename 的 RAW+JPG；与 dHash 去重并存（去重=可删，堆叠=合并浏览），严守「程序内不删除」红线。
- [ ] 中优先项（层级标签 / XMP / 完整性校验 / 归档）本迭代不排期，留待下迭代评估。
- [x] ⚪ 类功能（多用户/共享/移动备份/回收站自动清空/视频转码/非破坏修图）明确**不做**，写入需求边界（`docs/iteration_plan.md` §6）。

> 合并迭代计划见 **`docs/iteration_plan.md`**（C5 迭代：①+②+③，分 M1/M2/M3 里程碑，待确认后进入 dev doc → 代码变更）。
